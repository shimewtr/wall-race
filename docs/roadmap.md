# 進め方と次にやること

このプロジェクトの目的・現状・次にやること・運用上の約束ごとを 1 か所にまとめたもの。
作業を再開するときはまずこのファイルを読む（末尾に再開用のプロンプトがある）。
AI 学習の経緯と詳しい継続手順は [training.md](training.md) にまとめている。

## 目的

1. 自己対戦で強い AI を作る
2. 「どう考えれば強くなれるか」を、人間が実行できる抽象的な手順として文章化する（[guide.md](guide.md)）
   - 手引きの良し悪しは「手引きどおりに打つだけの AI」（手引き AI）の勝率で測る

## 次にやること（優先順）

### 1. 学習を安定させる

高速化後の 35 ランでは 1 台 45 分あたり平均 118 反復（ランナー別 100〜138）、4 台合計で 1 サイクル約 470 反復になった。従来の 40〜80 反復からほぼ 2 倍で、`bench.ts` の選択手ハッシュも変更前後で `b4bec419` のまま。

一方、判定 9 回中 6 回リセットし、対チャンピオン勝率が 7.8〜54.5% と不安定だった。4 台が同じ始点から学習した差分を合算するため、リセット直後の学習率を `2` から `0.5` に下げたが、その後も 3 回中 2 回リセットしたため `0.25` へ下げた。

- **揺らし幅の実験完了**: `PERTURB` の倍率を `1.0` から `0.5` に下げた最初の6判定は平均54.7%、範囲43.8〜60.5%、リセット1回。従来の直近9判定（平均47.8%、リセット3回）より安定したため0.5を継続する
- 0.5倍での17判定は平均50.8%、リセット2回、昇格3回。第9世代昇格後の直近11判定は平均48.6%、範囲46.3〜50.5%、リセット1回で、振れは小さくなったが第9世代付近で停滞している。最新判定は対第9世代49.3%、対初期79.5%
- 現条件を継続し、再び6判定中2回以上リセットするようなら、1反復16組の対局数を増やして勾配のばらつきを減らす

### 2. AI をさらに強くする

- **新しい特徴量を試す**: 手引き作りで見つかった考え方を AI に入れると強くなった実績がある（`wallThreat`）。候補は次のとおり
  - 最短ルートの本数: `routeDiversity=5` が当時のチャンピオンに **58.5% ±4.8**（400 局）。計算結果をキャッシュして、選択手ハッシュを変えずに 20.1 → 15.9ms/手まで高速化し、`PERTURB=2` で学習対象に追加した。第8世代では2.577、第9世代への昇格時には0.041まで学習で下がったため、現在のリセットは第9世代の値を基準にする
  - 4 歩以上の壁脅威: 手引きで有効だった閾値を `severeWallThreat` として試したが、重み 2.5 / 5 / 10 はチャンピオンに 43.0% / 41.3% / 35.8%（各400局）で全敗。探索の評価値には採用しなかった
  - 守りの壁: 広い候補の勝率は狭い候補に対して3手読み49.5%、4手読み50.9%（各400局）で互角。狭い候補は3手20→3ms、4手50→13msに短縮できたため既定値に採用。第7世代300局で守りの壁は全壁の6.4%だった
  - 最後の壁を残す価値: 第7世代300局では先に壁を使い切った側の勝率が24.3%（218局）だったが、単純な `wallReserve`（壁を1枚以上持つ価値）の重み10 / 20 / 40は47.5% / 45.8% / 42.5%（各400局）で全敗。既存の壁関連特徴と役割が重なるため不採用
  - 試し方: 特徴量を追加して重み 0 で入れ、`compare.ts` で「チャンピオン＋その特徴量」対「チャンピオン」を比べる。勝ち越したら学習の対象（`PERTURB`）に入れる
- **読みの深さ**: 80局面の実測は3手1.33秒、4手3.31秒、5手16.06秒。4手読みは3手読みに70.5% ±4.5（400局）だったためWebの「つよい」に採用。5手読みは3手の約12倍なので見送った。学習・昇格判定は従来どおり3手読み
- **ランナーを増やす（要判断）**: 4 台 → 8 台で学習量は 2 倍になる。GitHub Actions の利用規約上、計算を回し続けるのはグレー寄りなので、増やすかはユーザーが判断する

### 3. 手引きを改良する

- **最新世代に勝てない理由を探す**: 手引き AI が最新世代に負けた対局で、チャンピオンと手引き AI の選ぶ手が食い違った局面を集め、手引きに足りない考え方を探す
  - `discover.ts` で盤面・両者の手・探索上の推定損失・勝敗を収集し、LLM で戦術候補を抽出する。候補は手引きなら `guide.ts --opponents league`、AI の特徴量なら `compare.ts` 400 局以上で検証する
  - 第 7 世代との 120 局から「壁の使いすぎ」と「大きな壁脅威への守り」を発見。全世代リーグ各100局で、第 4 版 47.8% → 第 5 版 55.4% を確認して採用した
  - 第 5 版で300局を再分析すると第7世代に56.0%。推定損失上位30局のうち少なくとも17局は自分の壁が残り1枚だった。最後の壁に追加1 / 2 / 4歩のコストを付けると全世代リーグ平均66.5% / 66.8% / 64.4%（第5版55.4%）。追加2歩を第6版として採用した
  - 第 6 版は第8世代との120局で60.0%。敗戦中の有意な判断差341局面には、壁が尽きた後に同じ2マスを往復する例が繰り返しあった。戻る手のコスト0.5歩は全世代リーグを68.4%から71.4%へ改善したため第7版として採用。1歩は平均73.9%だが第8世代への合算が68%から54%へ落ちたため不採用
  - 第 7 版は第9世代との120局で64.2%。敗戦中の有意な判断差729局面のうち、壁を選んだが探索AIは前進を選んだ局面が166、逆が29で、壁の使いすぎが約5.7倍多かった。しかし全局面の壁コスト0.75 / 1.0は全世代リーグ各50局で66.5% / 66.8%（現行71.7%）、先着できる局面だけの追加コスト0.5 / 1.0は44.6% / 37.4%（現行71.7%）、4歩以上 / 8歩以上リード時だけの追加0.5も各40局で69.8% / 68.3%（現行71.0%）に悪化したため、単純な壁抑制は不採用。次は推定損失の大きい壁→壁31局面から、壁の置き場所の規則を探す
  - 壁→壁の上位局面には、手引きの縦壁に対して探索AIが横壁で複数の迂回路をまとめて絞る例が繰り返しあった。しかし返し手後の最短ルート本数差を評価する候補0.25 / 0.5は、全世代リーグ各40局で47.2% / 48.3%（現行71.0%）、第9世代3手では13% / 33%（現行65%）に悪化したため不採用。経路本数だけを追うと肝心の距離や壁への耐性を損なう
  - 第9世代との標本を240局へ増やすと手引きは66.3%。壁→壁43局面では、探索AIの壁は即時の正味遠回りが手引きより良い例が0件で平均0.84歩小さい一方、次の壁脅威は18件、経路の柔軟性は21件で改善した。探索AIは即効性より数手先の壁の連携を選んでいる。ただし壁候補間だけで次の壁脅威を追加評価する0.25 / 0.5は全世代リーグ各40局で63.1% / 62.4%（現行71.0%）へ悪化したため不採用。単一指標ではなく壁の応酬を読む必要がある
  - 手引きの再帰読みを2段から3段へ増やす予備測定は、全世代リーグ各10局で64.4%（現行68.9%）。小標本でも改善せず、360局で21分42秒と通常の約7倍/局以上かかったため不採用
- **世代が進んだら測り直す**: 第7版は第9世代を含むリーグで平均70.9%を確認済み。第7世代の自己対戦300局も取得済み（先手50.3%、平均73.7手、守りの壁6.4%、先に壁を使い切った側24.3%）なので、次の大きな世代更新時に再計測する
- **まだ分かっていないこと**（guide.md 末尾）: 守りの壁の使いどころ、「相手の一番いやな返し」や「壁 1 枚で遠回りさせられる歩数」を盤面で素早く見つけるコツ
- **読みやすくする**: 盤面の図や具体例を入れる。Web から手引きを読めるようにする

## 運用上の約束ごと

- **手元の Mac では学習・対戦ベンチなどの重い処理を回さない。** 重い処理は GitHub Actions で回す
  - 学習: Train ワークフロー（連鎖実行。止めるときは `gh variable set TRAIN_CHAIN --body off`）
  - 実験: Experiment ワークフロー。`gh workflow run Experiment -f script=<scripts/experiments のファイル名> -f args="..."`。結果はログとサマリーに出る
  - 手元では数秒で終わる `npm test` / `npm run build` だけ
  - Web の見た目の確認は、push して GitHub Pages に反映されたものをブラウザで見る（キャッシュを避けるため URL に `?v=<コミット>` を付ける）
- **数字で確かめてから変える。** 探索の高速化は `bench.ts` の「選んだ手のハッシュ」が変わらないことを確かめる。AI の変更は `compare.ts`（400 局以上）、手引きの変更は `guide.ts --opponents league` で比べる
- **特定の相手に合わせない。** 手引きは全世代の平均で、AI の昇格は対チャンピオンと対初期の重みの両方で判定する
- **展開をばらけさせる。** 自己対戦の序盤 6 手は上位 3 手からランダム。これが無かったころの統計は同じ展開の繰り返しで偏っていた
- コミットの作者は GitHub の noreply アドレス（公開リポジトリに会社のメールを出さない）。ゲームの元になった商品の名前は使わない
- 返答・ドキュメントは日本語

## 再開するときのプロンプト

別のセッションで再開するときは、次をそのまま貼る（`<やりたいこと>` は書き換える）。

```text
~/ghq/github.com/shimewtr/wall-race で作業を再開したい。
まず docs/roadmap.md、docs/training.md、docs/guide.md、README.md を読んで、目的・現状・これまでの学習・次にやること・運用上の約束ごとを把握して。
そのうえで `git pull` して `npm run status` と `gh run list --limit 10` で学習と Actions の最新の状況を確認し、
roadmap.md の「現状」から変わったところと、「次にやること」のうち今やるべきものを日本語で短く報告して。

約束ごと:
- 手元の Mac では学習や対戦ベンチなど重い処理を回さない。重い処理は GitHub Actions（Train / Experiment ワークフロー）で回す。手元は npm test / npm run build だけ
- 変更は数字で確かめる（高速化は bench.ts のハッシュ一致、AI は compare.ts、手引きは guide.ts --opponents league）
- 返答は日本語

今回やりたいこと: <やりたいこと。特になければ「roadmap.md の次にやることを上から進めて」>
```

作業の区切りでは、このファイルの「現状」と「次にやること」を更新しておく。
