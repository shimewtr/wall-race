# AI 学習の記録と継続手順

AI の学習を別のセッションでも同じ方針で続けるための手順書。
最新世代・直近の数値・次の課題は [roadmap.md](roadmap.md)、学習アルゴリズムの実装は [`scripts/train.ts`](../scripts/train.ts) を正とする。

## どこに何があるか

| ファイル | 役割 | 更新するタイミング |
| --- | --- | --- |
| `training/state.json` | 学習中の重みと累計反復数 | Train が毎回自動更新 |
| `training/history.jsonl` | 実行ごとの反復数・判定勝率・昇格・リセット | Train が毎回自動追記 |
| `training/champion.json` | 現チャンピオン | 昇格時に Train が自動更新 |
| `training/champions/gen-NNNN.json` | 各世代の保存版 | 昇格時に Train が自動追加 |
| `training/calibration.json` | 評価値を勝率へ換算する式 | 昇格時に Train が自動更新 |
| `docs/roadmap.md` | 現状、確定した実験結果、次にやること | 作業の区切りごと |
| `docs/analysis.md` | 新しい戦術・特徴量・学習方法を探す分析カタログ | 分析手法や優先順位を追加・変更したとき |
| `docs/training.md` | 学習方法、運用手順、再開方法 | 学習方式・判定条件・運用が変わったとき |
| `README.md` | 利用者にも関係する仕組みと使い方 | Webの強さや主要な仕組みが変わったとき |
| `docs/guide.md` | 人間向けの戦術 | `guide.ts --opponents league` で採用を決めたとき |

`training/` は Train が commit・push するため、通常は手で編集しない。

## これまでの学習

### 1. 評価関数を SPSA で調整

探索 AI の評価関数を「残り歩数」「残り壁」「終盤の緊急度」などの重みベクトルにし、自己対戦で重みを更新してきた。
1反復では、重みを少しずつプラス・マイナスに振った2つの候補を、同じ相手・同じ乱数条件で各64組対戦させ、勝率差の方向へ進める。16組では128組基準の勾配と同符号になる割合が55.7%だったが、64組では81.8%に改善したため、反復数より方向の確かさを優先している。

- `pathDiff` は「1歩 = 10点」の基準として固定
- 対戦相手は50%が現チャンピオン、残りは初期値を含む過去世代から無作為
- プラス側とマイナス側を直接戦わせず、共通の相手と比較して局所的なじゃんけんを避ける
- 学習・昇格判定は3手読み

### 2. 展開をばらけさせた

同じ序盤ばかり学ぶ偏りを避けるため、序盤6手は評価上位3手から無作為に選ぶ。この区間だけは計算量を抑えるため2手読み。その後は最善手から0.1歩以内の手を無作為に選ぶ。

### 3. 昇格とリセットを数値で判定

学習中の重みを現チャンピオン・初期重みと各400局対戦させる。

- 現チャンピオンに55%以上なら昇格候補
- 52.5〜55%なら現チャンピオン戦だけ1200局を追加し、合計1600局で52.5%以上なら昇格候補。第11世代への400局判定が27回連続48.4〜54.5%だった一方、独立した1600局では53.3% ±2.4となり、単発55%だけでは小さいが再現性のある改善を採用できなかったため追加した
- 初期重みへの勝率が現チャンピオンより3ポイント以上悪化したら昇格させない
- 現チャンピオンへの勝率が47%未満なら、チャンピオンを基準に学習をやり直す

### 4. GitHub Actions で4台並列化

Train ワークフローは4ランナーで45分ずつ学習する。ランナー2〜4は重みの差分を足し込み、最後のランナー1だけが昇格・リセットを判定する。終了時に次のTrainを起動し、`TRAIN_CHAIN=on` の間は連鎖する。

4台分の差分を合算すると振れが大きくなったため、学習率を `2 → 0.5 → 0.25` と下げた。さらに特徴量の揺らし幅を0.5倍にし、安定性を観察している。

### 5. 分析から新しい特徴量を追加

棋譜や手引きとの判断差を分析して仮説を作り、必ず400局以上で比較してから学習対象へ入れる。

- `wallThreat`: 壁1枚が作れる遠回りの差。比較で有効だったため採用
- `routeDiversity`: 最短ルートの豊富さ。重み5が当時のチャンピオンに58.5%（400局）で学習対象へ追加。学習後は第8世代で2.577、第9世代で0.041となり、固定値ではなく他の特徴量と一緒に調整されている
- `wallChain`: 壁2枚の総迂回から最善の1枚分を引いた追加効果。重み2が第9世代に55.0%（400局）。1枚目を即時効果最大の候補だけに絞ることで、平均思考時間を19→9ms/手に抑えて学習対象へ追加した。2サイクル後に重み1.845、対第9世代56.3%で第10世代へ昇格。さらに学習を続け、重み3.342、対第10世代56.8%で第11世代へ昇格した。第10世代では1枚目の最善壁と2枚目の計算を通常キャッシュから再利用し、選択手ハッシュを変えずに14.3→6.6ms/手、全4コア1.61→3.56組/秒へ高速化した
- `netWallThreat`: 相手への遠回りから自分への遠回りを引いた、正味の壁脅威。重み5が第11世代に52.9% ±2.4（1600局）。更新不能な候補では自分側の経路探索を省き、400局103→55秒（通常AIは約49秒）まで短縮して、初期重み5・`PERTURB=2` で学習対象へ追加した
- `severeWallThreat`: 4歩以上の脅威だけを分けた候補。重み2.5 / 5 / 10が43.0% / 41.3% / 35.8%で不採用

探索の深さも比較し、4手読みは3手読みに70.5%（400局）だったためWebの「つよい」に採用した。ただし学習を4手読みにすると計算量が約2.5倍になるため、学習・昇格判定は3手読みを維持している。5手読みは3手読みの約12倍なので見送った。

根でコマ周り・自分の経路沿いの壁まで候補にする広い探索は、狭い探索に対して3手読み49.5%、4手読み50.9%（各400局）で差がなかった。狭い探索は思考時間が3手20→3ms、4手50→13msになったため既定値にし、判定条件の識別子にも根の候補範囲を含めた。

## 現在の学習運用

1. GitHub Actions の Train が4台並列で学習する
2. 各ランナーが終了時に最新の `training/` を取り込み、自分の差分だけを加える
3. ランナー1がチャンピオン・初期重みとの対戦を行う
4. 条件を満たせば新世代へ昇格し、勝率換算式も更新する
5. `training/` を自動で commit・push する
6. `TRAIN_CHAIN=on` なら次のTrainを起動する

終了時のpull/pushは、一時的なGitHub接続障害で1回の学習結果と連鎖全体を失わないよう、1回60秒を上限に最大3回再試行する。全ランナーが失敗しても毎時のscheduleが連鎖の保険になる。

重い処理はすべて Actions で行う。手元の Mac では `npm test` と `npm run build` だけを実行する。

## 今後の優先順

最新の優先順と数値は必ず [roadmap.md](roadmap.md) を確認する。基本方針は次のとおり。

1. 揺らし幅0.5倍・1反復64組を継続する。64組化後60判定は47.0〜54.6%でリセット0回。二段階ゲートの合計1600局で第11世代に54.6%、初期重みに85.3%となり第12世代へ昇格した。昇格後109判定は48.0〜52.4%（平均50.7%）でリセットなしだが、約22,000反復進めても昇格していない
   - 停滞対策として、現在位置の継続・学習率の再加熱・チャンピオンからの再出発を `restart-training.ts` で比較した。48反復×3 seed・各400局では、継続対再出発が対チャンピオン51.0%対50.2%、対初期83.7%対85.2%、歴代混合65.5%対64.1%。再出発は主要2指標で継続を下回るため不採用とし、Trainの方式は変えない
   - 次の律速だった `shortestDistance` は、壁判定の直接展開で選択手ハッシュを維持したまま同時刻ベンチ10.8→7.0ms/手、1.40→3.11組/秒へ改善した。導入後のTrain反復数も観察する
   - `shortestPath` も同じ方法で直接展開し、ハッシュを維持したまま6.8→6.1ms/手、2.62→2.89組/秒へ改善した。次の連鎖runから両方の高速化が入る
   - Webの4手読みも選択手ハッシュ `98d8e83c` を維持したまま33.0→18.4ms/手、全4コア0.96→1.53組/秒へ改善した
2. `netWallThreat` は導入後29回目の判定で第12世代へ昇格した。採用重みは3.906（0.391歩分）。昇格後は5.062（0.506歩分）まで調整されているため、学習を継続する
3. 「壁1枚で歩数負けを先着可能へ変えられるか」を表す `wallRescue` は、重み2.5 / 5 / 10が第12世代に46.8% / 43.3% / 41.5%（各400局）で全敗したため不採用。学習を継続しつつ、棋譜のLLM分析から既存特徴と重ならず、最終的な勝ち筋を表す次の特徴量候補を作る
4. 棋譜のLLM分析から特徴量候補を作る。単純な `wallReserve` は重み10 / 20 / 40が47.5% / 45.8% / 42.5%（各400局）で全敗したため、最後の壁は既存特徴と重ならない局面依存の表現を探す
5. 候補は重み0で追加し、`compare.ts` 400局以上で有効性を確認する
6. 勝ち越した候補だけ `PERTURB` と学習の基準値へ入れる
7. 第12世代の再計測と判断差分析は完了。前進同士191局面から、壁切れ後だけ戻る手のコストを2歩へ強める第8版を作り、全世代リーグ各100局で68.7%→69.9%、第12世代2手73%・3手49%を確認して採用した。壁→前進220局面の単独・複合減点、前進→壁56局面の緊急防御、壁→壁60局面の歩数不利時の弱い壁抑制はいずれも全世代平均を改善せず不採用。さらに候補手ごとに終局まで指す反実仮想分析を追加し、壁→壁46局面のうち3・4手読みとも勝敗改善11と判定した。改善局面では同方向の2枚目を短期間で置く連結壁が目立ち、その正味効果は4手読みでも改善3.82・非改善0.57だった。ただし個別局面の複合条件は読みの深さで精度が落ち、全1枚目候補から連結2枚目を調べる `wallExtension` も第12世代に最大51.5%（各400局）、計算約4〜8倍で不採用。今後は実際の勝敗を変える連携を優先しつつ、既存探索の候補選択内で安く表現する

## 学習セッションの開始手順

```sh
git pull --rebase
npm run status
gh variable get TRAIN_CHAIN
gh run list --limit 10
gh run list --workflow Train --limit 10
```

確認すること:

- 現チャンピオンの世代と対初期勝率
- 累計反復数、学習中の重み、直近の昇格・リセット
- Train が `queued` / `in_progress` か
- `TRAIN_CHAIN` が `on` か
- [roadmap.md](roadmap.md) の現状と次の作業が実データと一致しているか

Train が動いておらず、継続する意図なのに待機中なら、重複実行がないことを確認してから起動する。

```sh
gh workflow run Train -f minutes=45
```

## 実験から採用まで

### 学習の安定性を変える場合

1. 変更前の判定勝率・標準的な反復数・リセット回数を `training/history.jsonl` から記録する
2. `scripts/train.ts` の変更は一度に1要因に絞る
3. `npm test` と `npm run build` を手元で実行する
4. push後、Trainを複数サイクル回す
5. 同じ判定回数で変更前後を比較し、roadmapへ結果を書く

120分に近づく長時間実験は、完了単位ごとに `experiment-progress.jsonl` と `experiment-output.json` を更新する。Experimentはキャンセル・タイムアウト時もこれらをartifactへ保存する。対応スクリプトを再開するときは、同じコミット・同じ引数に `--resume-file experiment-progress.jsonl` を加え、workflowの `resume_run`へ再開元run IDを渡す。世代・開始重み・実験条件が一致しない場合は安全のため再開を拒否する。

### 新しいAI特徴量の場合

1. 棋譜・`analyze.ts`・`discover.ts` から仮説を作る
2. 特徴量をデフォルト重み0で追加する
3. 重み0の `bench.ts` で選択手ハッシュが変わらないことを確認する
4. 複数の重みを `compare.ts` で各400局以上比較する
5. 勝ち越した場合だけ学習対象に追加する。不採用結果もroadmapに残す

### 手引きの場合

1. `discover.ts` のログをLLMで分類し、人間が実行できる規則にする
2. `GUIDE_CURRENT` にはまだ入れず候補パラメータとして実装する
3. `guide.ts --opponents league` で過去の全世代×2・3手読みを相手に比較する
4. 全世代平均で改善した候補だけ `GUIDE_CURRENT` と `docs/guide.md` に同時反映する

## 作業終了時の更新手順

作業のたびに、次を確認してから終了する。

1. Actions が更新した場合は `git pull --rebase` して `npm run status` を取り直す
2. 実験結果を採用・不採用の両方とも `docs/roadmap.md` に数値付きで記録する
3. 学習率・揺らし幅・対局数・昇格条件・並列構成を変えたら、この `docs/training.md` とコード内コメントを更新する
4. 利用者に見えるAIの強さ・操作・主要機能が変わったら `README.md` を更新する
5. 人間向け戦術を採用したら `src/guide/policy.ts` と `docs/guide.md` を同時に更新する
6. `docs/roadmap.md` の「現状」と「次にやること」から完了事項・古い予定を整理する
7. `npm test` と `npm run build` を実行する
8. `git diff --check` と `git status` を確認し、noreplyアドレスの作者で commit・push する
9. CI・Pagesが必要な変更はActionsの成功まで確認する

自動Trainの各ランごとにREADMEを書き換える必要はない。昇格、方式変更、実験の採否、作業セッションの区切りなど、人が後から判断に使う節目では必ず上の対応ファイルを更新する。

## 別セッションで再開するときの文章

次を新しいセッションへそのまま貼る。

```text
~/ghq/github.com/shimewtr/wall-race で AI 学習を継続したい。

最初に README.md、docs/roadmap.md、docs/training.md、docs/guide.md を読み、目的・これまでの学習・現在の方式・最新世代・次の実験・運用上の約束を把握して。
次に git pull --rebase、npm run status、gh variable get TRAIN_CHAIN、gh run list --limit 10、gh run list --workflow Train --limit 10 を実行し、ドキュメントとの差分と今やるべき作業を日本語で短く報告して。その後、roadmap.md と training.md の優先順に従って自律的に進めて。

約束:
- 手元の Mac では学習・対戦ベンチ・分析などの重い処理を回さない。重い処理は GitHub Actions の Train / Experiment で行い、手元では npm test / npm run build だけ実行する
- 変更は数字で検証する。高速化・挙動維持は bench.ts の選択手ハッシュ、AIは compare.ts 400局以上、手引きは guide.ts --opponents league で判定する
- 特定の相手だけに合わせず、AIの昇格は現チャンピオンと初期重み、手引きは過去の全世代で評価する
- 実験は一度に1要因を変え、採用・不採用の両方を数値付きで残す
- 作業の区切りでは、Actionsの更新をpullしてから docs/roadmap.md の「現状」「次にやること」を更新する。学習方式や運用を変えたら docs/training.md、利用者向け仕様を変えたらREADME.md、戦術を採用したら src/guide/policy.ts と docs/guide.md も同時に更新する
- training/ はTrainが自動更新するので、通常は手で編集しない
- コミット作者はGitHubのnoreplyアドレスを使い、返答とドキュメントは日本語にする
```
